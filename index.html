01 · The problem

The fastest block to read
is the one you never read.

Columnar formats (Parquet, ORC, DuckDB, ClickHouse) split tables into blocks and keep min/max per block. A query skips a block if the value can't be inside the range. That works on sorted data, and fails on shuffled data.

WHERE user_id = 501

Block = row group

Parquet row group, ORC stripe, ClickHouse granule. The unit that can be skipped as a whole.

Min/max is weak here

High-cardinality columns that are not sorted: every block covers almost the full range.

Real effect

DuckDB example, value absent but inside min/max: 0.1 s → 0.002 s with a 47-byte filter per row group.

02 · How a Bloom filter works

A bit array that answers “definitely no”
or “probably yes”.

Insert: hash the key with k = 3 functions, set those bits. Query: if any bit is 0, the key was never inserted.

Block contains: try querying a value.

Why it is safe for pruning

Bits are only ever set, never cleared, so no false negatives. A false positive only costs one unnecessary read; the query result stays correct.

bits/key ≈ 1.44 · log₂(1/ε)

≈ 10 bits per key for a 1% false-positive rate, about 7 hashes. That is 44% above the theoretical minimum.

In Parquet today

Split Block Bloom Filter: one per column chunk, 256-bit blocks, 8 bits set via XXH64, one cache line per probe. Used by DuckDB, Impala, Spark, ClickHouse.

03 · Modern alternatives

Bloom isn't the only filter. Newer ones
trade build cost for space.

04 · What “memory–performance” means here

Filter bytes in memory
vs. work we don't do.

Cost: memory

The filter's size: bits per key × keys per block. Usually kept resident, so it competes with cache for space.

+ probe CPU  + build time

Plus a false-positive rate, which means unnecessary reads.

vs

Benefit: avoided work, by where the block lives

Object storage (S3)remote GET avoided: biggest win
Local disk / SSDblock I/O avoided
Already in RAMdecompression + scan CPU avoided

The gain is clearest when the filter lets us skip a block on disk. In-memory uses exist too, but they are a different, smaller saving, and we measure them separately.

05 · Plan

Small, controlled, and stoppable after each step.

STEP 1

Synthetic columns

Control the order (sorted vs shuffled), cardinality, skew, and whether the value is absent but inside min/max.

STEP 2

Filters per block

Bloom / SBBF as the baseline vs binary fuse. XOR as an optional third.

STEP 3

Measure

Bits per key · real false-positive rate · blocks pruned beyond min/max. Later: I/O bytes, probe and build time.

STEP 4

Real data

One column from TPC-H or ClickBench. Equality and IN queries; ranges only if SuRF is added.

06 · Expected outcomes (hypotheses, not results)

What we expect to see.

H1

Shuffled columns: filters prune many blocks that min/max cannot.

H2

Sorted columns: filters add little on top of min/max.

H3

Binary fuse / XOR use fewer bits per key than Bloom at an equal false-positive rate.

H4

…but are slower to build, which matters for blocks queried rarely.

H5

No single winner across space, build, probe and predicate type.

Out of scope
inventing a new filter compression / ANS declaring a universal winner range filters in iteration 1
